# Сёрфинг

Панель торгового робота для песочницы Т‑Инвестиций. Доступны настройка виртуального счёта и стратегии, живой график котировок, торговля по пересечениям EMA и журнал исполнений.

## Запуск через Docker Compose

1. Скопируйте `.env.example` в `.env`. Задайте `OWNER_PASSWORD` (12–256 символов) и `POSTGRES_PASSWORD`; используйте разные пароли. Выполните `openssl rand -hex 32` и поместите результат в `SANDBOX_TOKEN_KEY`.
2. Выполните `docker compose up --build -d`.
3. Откройте `http://127.0.0.1:8080` и введите пароль владельца. Если задан `FRONTEND_PORT`, используйте его.

Миграции запускаются при старте бэкенда. PostgreSQL хранит данные в именованном томе; `docker compose down` останавливает приложение без удаления данных. Через внешний порт доступен только фронтенд, и только на loopback. Для HTTPS установите `COOKIE_SECURE=true`.

## Подключение песочницы

В панели владельца введите действующий токен песочницы Т‑Инвестиций и нажмите «Проверить и сохранить». Выберите выделенный виртуальный счёт или создайте новый; новый счёт выбирается автоматически. Кнопка «Пополнить на 100 000 ₽» зачисляет виртуальные рубли на выбранный счёт. Если пополнение не подтверждено, проверьте баланс в песочнице перед повторной попыткой.

Чтобы проверить подключение с действующим токеном, выполните эти шаги, перезапустите бэкенд (`docker compose restart backend`) и обновите панель. Подключение и выбор счёта должны восстановиться, а поле токена остаться пустым. Бэкенд использует gRPC-клиент официального `invest-js` (`@ttech-pub/grpc-node-client`) только с адресом песочницы. Для проверки её TLS-сертификата SDK загружает сертификат Минцифры с `gu-st.ru`; бэкенду нужен исходящий HTTPS-доступ к этому адресу.

Не меняйте `SANDBOX_TOKEN_KEY` при перезапуске. Храните его отдельно от базы и её резервных копий. При потере ключа сохранённый токен нельзя прочитать: задайте новый ключ и введите токен заново.

Отправка токена — исключение из обычных мутаций RTK Query: форма отправляет секрет напрямую в REST API, чтобы он не попадал в действия Redux и Redux DevTools. После сохранения интерфейс обновляет данные подключения через RTK Query.

## Настройки стратегии

После выбора виртуального счёта найдите фьючерс по тикеру или названию и выберите конкретный контракт. По умолчанию панель ищет `IMOEXF` и предлагает период EMA `55`; объём позиции в лотах задаёт владелец. Если тикеры совпадают, сверяйте биржу, дату экспирации и UID в списке. После сохранения и перезапуска панели восстановятся тот же контракт, период и объём.

## Живой график

После сохранения настроек панель загружает часовые свечи за последние семь дней. Время на графике — начало свечи в UTC. Сплошная линия показывает EMA от `GetTechAnalysis` только для закрытых свечей с совпадающей меткой времени; пунктир показывает предварительную EMA текущей свечи, если есть подтверждённая точка для расчёта. Если EMA ещё не поступила, панель не заменяет её оценкой для закрытой свечи.

График построен на [TradingView Lightweight Charts](https://www.tradingview.com/lightweight-charts/). Наведите указатель, чтобы увидеть время и четыре цены свечи: открытие, максимум, минимум и закрытие. Колесо мыши меняет масштаб по времени, перетаскивание графика прокручивает историю, а перетаскивание правой шкалы меняет масштаб цен. Кнопка «К последней свече» возвращает к актуальным котировкам.

Поток котировок работает независимо от состояния робота. Во время торгов повторные обновления меняют текущую свечу, не добавляя её заново. После обрыва панель переподключается и догружает историю. Для отдельной проверки контракта песочницы установите через окружение `SERFING_TEST_SANDBOX_TOKEN` и `SERFING_TEST_FUTURE_UID` (UID активно торгуемого фьючерса) и выполните из `backend/` `npx tsx --test src/infra/invest-sandbox.market.test.ts` во время торгов. Тест проверяет совпадение временных меток EMA и свечей, подтверждение подписки и получение живой свечи. Он не выставляет заявок.

## Первый вход и журнал

Выберите выделенный счёт песочницы, сохраните инструмент и нажмите «Запустить робота». Для старта нужна нулевая позиция по выбранному фьючерсу и отсутствие активных заявок на счёте. История задаёт исходную сторону EMA, но не создаёт заявок. Первое подтверждённое пересечение после запуска выставляет одну рыночную заявку на заданное число лотов. Закрытие вкладки не останавливает робота. «Остановить робота» не закрывает позицию.

Журнал показывает цену закрытия и EMA отдельно от цен и времени исполнения. При обрыве потока брокера запущенный робот ждёт догрузки свечей и EMA. Пересечения за время разрыва не создают заявок. Если закрылась только вкладка или пропала связь с браузером, робот продолжает работать на сервере.

При проблеме с заявкой нажмите «Сверить заявку», чтобы запросить её статус по исходному клиентскому ID и проверить фактическую позицию. Заявка при этом не отправляется повторно. Если статус или позиция не подтверждены либо на счёте есть активная заявка, возобновление заблокировано. После перезапуска сервера робот сверяет позицию и нерешённую заявку, но остаётся остановленным. Если прежний токен недействителен, его можно заменить токеном с доступом к тому же счёту и повторить сверку. Для продолжения нужна команда владельца: «Запустить робота» или, после успешной сверки заявки, «Возобновить торговлю».

Для отдельной smoke-проверки выставления заявки запустите из `backend/` `npx tsx --test --test-name-pattern="explicit sandbox smoke" src/infra/invest-sandbox.trading.test.ts` во время торгов. Передайте `SERFING_TEST_PLACE_SANDBOX_ORDER=yes`, `SERFING_TEST_SANDBOX_TOKEN`, `SERFING_TEST_FUTURE_UID`, `SERFING_TEST_SANDBOX_ACCOUNT_ID` и `SERFING_TEST_DATABASE_URL`. Используйте отдельный пополненный виртуальный счёт без позиции и заявок и отдельную тестовую PostgreSQL. Проверка отправляет **одну виртуальную покупку на один лот**, сохраняет исполнения и оставляет позицию открытой. Перед повтором проверьте счёт и журнал.

## Разработка в Docker с автообновлением

Нужен Docker Compose 2.32 или новее. Создайте корневой `.env` с паролями, как описано выше, и запустите:

```sh
docker compose -f compose.dev.yaml up --build --watch
```

Откройте `http://127.0.0.1:5173` (порт можно изменить через `DEV_FRONTEND_PORT`). React обновляется через Vite HMR при сохранении, а Node.js перезапускает бэкенд при изменении импортируемого кода. `/api` проксируется через Vite, поэтому вход и запросы работают с того же адреса. Изменения зависимостей пересобирают только соответствующий dev-образ.

Dev-проект использует отдельный том PostgreSQL и не затрагивает обычный запуск на порту 8080. Для остановки нажмите `Ctrl+C`. Чтобы убрать dev-контейнеры, сохранив данные, запустите `docker compose -f compose.dev.yaml down`.

## Разработка без сборки Docker-образов

Требуются Node.js 24+ и доступный PostgreSQL. Для каждого приложения скопируйте его `.env.example` в `.env`. В `backend/.env` задайте адрес БД, пароль владельца и ключ шифрования; в `frontend/.env` при необходимости измените адрес бэкенда для прокси Vite.

- `backend/`: `npm ci`, затем `npm run dev`; проверки — `npm run typecheck`, `npm test`, `npm run build`.
- `frontend/`: `npm ci`, затем `npm run dev`; проверки — `npm run build`, `npx playwright install chromium`, `npm test`. Тест браузера использует подменный REST API, если адрес приложения не задан.

Компоненты интерфейса добавляются из `frontend/` командой `npx shadcn@latest add <компонент>`. Настройки находятся в `frontend/components.json`, палитра светлой и тёмной тем — в `frontend/src/styles.css`.

Для браузерной проверки реального Compose-развёртывания запустите из `frontend/` `npm test`, передав через окружение `SERFING_E2E_URL=http://127.0.0.1:8080` и `SERFING_E2E_PASSWORD` с паролем тестового владельца.

## PostgreSQL и миграции

Бэкенд работает с PostgreSQL через Drizzle ORM. Для изменения схемы обновите описание таблиц и из `backend/` выполните `npm run db:generate -- --name <название>`, затем `npm run db:check`. Добавляйте в Git и миграцию, и её метаданные. Бэкенд применяет миграции при запуске; существующие тома с таблицей сессий пересоздавать не нужно.

`node scripts/test-compose.mjs` из корня проверяет миграции на чистой PostgreSQL, проксирование WebSocket через nginx и сохранение сессии после пересоздания бэкенда. Флаг `--legacy` дополнительно проверяет переход с прежней схемы без потери сессии. Скрипт создаёт и удаляет только своё временное Compose-окружение.

Чтобы включить интеграционные тесты шифрования и восстановления счёта и стратегии, передайте в `backend/` при запуске `npm test` переменную `SERFING_TEST_DATABASE_URL` с адресом отдельной тестовой PostgreSQL. Тесты применяют миграции и записывают данные; токен брокера не нужен.
